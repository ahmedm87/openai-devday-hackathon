# Waywise feature guide

## Guided planning

Choose a starting station and destination, then select a preference:

| Preference | TfL search | Order of returned options |
| --- | --- | --- |
| Quickest | Least time | Duration, then changes, then TfL walking-leg minutes |
| Less walking | Least walking | TfL walking-leg minutes, then duration, then changes |
| Fewer changes | Least interchange | Changes, then duration, then TfL walking-leg minutes |

Changing the preference clears stale results. Submit again to retrieve options for the new preference. The recommendation badge names the active preference. Zero reported walking-leg minutes do not mean no movement within stations.

## Ask Waywise

Examples:

- “Waterloo to Bank”
- “King’s Cross to Paddington with fewer changes”
- “Victoria to Stratford with less walking”
- “Same journey, but fewer changes” after a journey has been found

The assistant interprets a request with one bounded `plan_journey` function call. The server resolves station names against the real station list and calls the same planner as the guided form. There is no open-ended tool loop, separate routing engine or database.

### Clarification

If “Bank” matches a DLR and an Underground entry, choose a station from the displayed buttons. An explicit choice is validated against the candidates. If the starting station or destination is missing, the assistant asks for it and retains the other endpoint. You can type a more specific name instead of choosing a button.

Once a journey is found, its cards, map, route steps, weather, status and evidence update together. The guided form is synchronized to those endpoints and preference. Follow-up preference buttons reuse the current journey.

### Scope and fallback

- Journeys leave now and use TfL station endpoints.
- Chat supports quickest, less-walking and fewer-change preferences.
- Future departure times, fares, specific-line avoidance, accessibility requirements and arbitrary addresses are not applied; the assistant explicitly identifies that limitation.
- Weather and disruption details come from the planner, not the language model's memory.
- Transport explanations still use the verified evidence catalog. Chat messages about the result are generated by the application from the actual planner result.
- Chat history is held in the browser page and limited to the six most recent messages sent with a request. There is no app-side chat database. Refreshing the page clears the conversation.
- The shared AI request cap covers intent parsing and evidence selection. If the limit or provider fails, the guided form remains available for usable transport facts.
- Chat is separate from the synthetic sample. Switch back to live mode before chatting.
